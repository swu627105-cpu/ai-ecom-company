AI 电商公司平台 · 功能清单与开发方案

把「一个主理人 + 一群 AI 员工」做成可交付的系统。清单覆盖 10 个模块、47 项功能，每一项都写明怎么实现（数据、接口、状态机、模型档位）与预估效果（可验收的口径）。原型里已经跑通的部分标注「已有」，其余为待建。

02

功能开发方案

每项：怎么实现 / 预估效果

A · 经营驾驶舱

4 项
功能怎么实现预估效果
A1 实时 KPI订单、退款、广告三类事件写入 Postgres，按 5 分钟窗口做物化视图；前端用 SSE 增量推送，不轮询。指标口径集中在 metrics 配置表，看板与 AI 读同一份定义，避免「前台价后台价打架」。原型已有静态卡片，需接真实数据源。主理人打开即见当日经营，不必等日报；AI 结论与看板数字同源，减少「数据对不对」的扯皮。
A2 沙盘 / 实时双模时间源抽象成 Clock 接口：实时模式取系统时间，沙盘取模拟时钟（原型里的倍速即沙盘）。同一套任务与会议状态机，切换模式只换时钟与连接器。新策略先在沙盘跑一遍再上真店；演示与生产共用一套代码，不会出现「演示很顺、上线不通」。
A3 事件流所有 AI 动作写 append-only 的 events 表（who / action / target / cost / trace_id），前端按时间线渲染，支持按岗位、任务、时间筛选。原型已有前端，需补落库。任何一个结论都能回答「谁、什么时候、基于什么数据做的」，复盘和追责有据。
A4 经营简报每日定时任务汇总 KPI 环比、异常事件、待办，走模型生成 300 字简报，经飞书卡片推送；生成失败降级为模板化文本。晨会前 3 分钟读完昨日经营，主理人不用自己翻看板。

B · AI 员工与任务

5 项
功能怎么实现预估效果
B1 AI 员工库agents 表存岗位、汇报关系、KPI、权限集、模型档位、SOP 引用；模型档位只是字符串键，由路由层解释。新增岗位＝插一条配置，不改代码。扩编从「改代码」变成「改配置」，一家店 12～15 个 AI 员工可随业务增减。
B2 任务派发三个入口统一进 tasks 表：手动指派、规则触发（如退款率 > 5%、库存 < 7 天）、目标拆解（CEO 幕僚把季度目标拆成子任务）。每条带幂等键，重复触发不重复建单。「该做但没人提」的事由规则兜住；同一件事不会因为重试被干两遍。
B3 执行与日志任务是有状态机（plan → act → check → done），每步落 steps 记录与 token 成本；工具调用统一走 MCP 注册表，白名单 + 参数 Schema 校验，越权直接拒。原型是脚本模拟，需换成真实编排。AI 干活过程可见，出错能定位到具体哪一步、哪次调用，而不是「它就是不太对」。
B4 任务回放按 trace_id 读取 steps 只读重演，工具调用回放为「假执行」，只展示当时入参与返回，不产生副作用。复盘不靠回忆；争议时能当场放一遍「当时是怎么做的」。
B5 重试与接管超时、429、置信度低于阈值 → 进 human_queue；支持一键重跑、换模型重跑、转人工执行。重试用指数退避 + 降级链，重试次数上限写死在配置里。限流或模型抖动不会让任务凭空消失，主理人只需要处理「确实需要人」的那一小撮。

C · 审批与决策

5 项
功能怎么实现预估效果
C1 审批卡approvals 表存方案摘要、影响面（订单/毛利/库存）、涉及金额、算力成本、附件；卡片按风险分级配色，高风险置顶。主理人 10 秒判断「要不要点开」，不被低价值审批淹没。
C2 决策依据强制六段结构：结论 / 指标 / 理由 / 风险 / 回滚 / 出处，用 JSON Schema 校验，缺字段直接打回重生成（最多两次，仍不合格转人工）。杜绝「AI 说可以」式空口建议，每条建议都必须能指出数据来源与回滚路径。
C3 拍板三态通过 → 调工具执行；驳回 → 理由写入偏好记忆并关闭任务；改条件 → 带新约束重跑方案，生成新版本而不是覆盖旧的。一次交互完成「同意 / 不同意 / 改一版」，且每次改动的版本可追溯。
C4 阈值与复核规则引擎判断金额、折扣幅度、预算占比、退款笔数；超阈值自动升级为双人复核或仅主理人可批。阈值按岗位与店铺配置。AI 不会自己把价格打到亏本；越权动作在提交前就被拦住，而不是事后补救。
C5 审计日志审批、执行、模型调用全量写入审计表，记录前一条哈希形成链式校验；支持按时间与主体导出 CSV/PDF。对内可交代、对外可举证；数据被改动能被发现。

D · 会议

7 项 · 原型已全部跑通
功能怎么实现预估效果
D1 召集与模板4 套模板（促销、退款政策、上新、自定义）存为议题数组；参会人默认按「谁受影响谁到场」推导，可手动增删，未参会者进书面意见通道。开会前不用想该叫谁，也不会漏掉真正会被影响执行的岗位。
D2 逐条发言会议状态机 setup → run → done，发言按岗位顺序串行输出，每条带 S.now 时间戳与岗位立场；前端流式渲染，可倍速。像真开会一样有先后与语气差异，能听出谁在担心什么。
D3 分歧识别发言结束后跑一次立场比对（规则 + 轻量模型），把「同一议题上结论相反的两方」配对成分歧块，附各自理由。分歧被显式摆到桌面上，而不是被平均成一段四平八稳的废话。
D4 三选项拍板由分歧生成保守 / 折中 / 激进三案，每案写清影响、代价、谁执行；点选后写入决议并锁定，不可再改（要改就再开一次会）。讨论能收敛成选项，决策从「再研究研究」变成「选一个」。
D5 纪要与行动项拍板 → 自动生成行动项（负责人、期限、风险等级）→ 派发为审批中心的真实任务卡，带本次会议的依据快照。会开完就有活，不用再写纪要追人；行动项与决策绑定，不会走样。
D6 书面意见 + 现场意见未参会 AI 只产出书面意见、不参与表决；主理人会议中输入框可随时插话，AI 按关键词匹配相关岗位当场回应，意见写入纪要并进入审批依据。会不因缺人而失真；主理人可随时纠偏，而不是等会后才推翻。
D7 会议回放与复用纪要与全部发言按议题打标签存档，检索时可按议题、商品、时间召回上次结论与当时的依据。同类议题第二次开会直接从上次的结论开始，不重复吵一遍。

E · 模型底座

5 项
功能怎么实现预估效果
E1 模型路由路由键 = 任务类型 × 时延要求 × 成本上限。视觉与长文档、长程推理走书生（端砚 /v1，OpenAI 协议）；高频对话走主力闭源；短分类、话术改写走本地小模型。档位写在员工配置里，可按任务覆盖。同样的活按性价比分配，视觉与长上下文用对模型，高频短调用不为大模型付溢价。
E2 降级链与熔断主 → 备 → 本地三级；429、超时、5xx 自动切换，失败计数触发 60 秒熔断；会议场景降级为「少发言但不断会」，不会卡在等模型返回。单家模型故障不影响开会与跑任务，最坏情况是输出变糙而不是停摆。
E3 成本计量每次调用记 token、模型单价、折人民币与墨点，按任务 / 岗位 / 店铺归集；预算闸门到顶自动降档或暂停，超额提醒主理人。算力成本变成可管理的经营科目，而不是月底才发现的账单。
E4 Prompt 版本管理Prompt 即配置：版本号 + 变更记录 + 灰度比例 + 一键回滚；每个版本绑定评测结果，未过评测不允许全量。改 Prompt 不再是玄学，效果不好能立刻退回上一版。
E5 评测集与回归固定 20 条真实任务（选品分析、差评归因、主图审核、会议发言等），每次换模型或改 Prompt 跑四项指标：JSON 合规率、工具调用成功率、P95 延迟、单任务成本。换模型有据可依；也顺带成为「书生能否升为主力档」的验收依据。

F · 知识与记忆

4 项
功能怎么实现预估效果
F1 商品知识库SKU、卖点、参数、资质结构化入库；图文向量存 pgvector，检索时带店铺与角色权限过滤，避免串店泄密。AI 谈商品不再编参数；主图与详情页审核有可比对的「官方卖点」。
F2 SOP 与话术库SOP 按岗位切成片段（退款话术、差评回复、上新检查单），任务开始时按需注入 2～3 段，而不是整本塞进上下文。输出更贴店内实际做法，同时把上下文成本压住。
F3 工单与评价检索历史工单与评价按店铺、品类、问题类型建索引，支持「同类问题上次怎么处理、结果如何」的相似检索。客服与评价 AI 的回答有先例可依，减少反复试错。
F4 主理人偏好记忆驳回理由、改条件、会议现场意见沉淀为偏好条目（如「不接受低于 30% 毛利」「大促前不压库存」），生成方案时自动带上并在依据中注明。越用越像懂你的下属，重复纠正同一件事的次数明显下降。

G · 工具与执行

5 项
功能怎么实现预估效果
G1 店铺连接器OAuth 授权 + 增量同步（订单、商品、退款、广告），限流按平台配额分配令牌桶，失败进重试队列；每家店一个连接实例，互不影响。多店并行不会互相拖垮；平台限流变成排队而不是报错。
G2 商品与价格改价与上下架走统一工具：先出差异预览（原价 → 新价、影响 SKU 数、预计毛利变化），确认后提交，提交前存快照支持一键回滚；幂等键防重复提交。改价不出错、可回滚；价格事故从「发现了再救」变成「点之前就知道后果」。
G3 营销与投放券、活动、投放计划先生成方案 → 预算校验 → 提交平台 → 定时回收效果数据 → 写回任务复盘。超预算直接走审批流。投放有闭环，不是「投完就忘」；预算超支在提交前被拦住。
G4 履约与售后发货、退款、售后工单接入工具层；大额退款、批量补偿强制走审批，执行结果回写订单状态。售后响应从小时级到分钟级，同时保留人工闸门防误伤。
G5 内容发布脚本 / 图文生成 → 合规检查 → 排期发布 → 数据回收；发布前需通过 H2 的合规校验。内容产能从「人天」压到「分钟」，且不会因极限词被下架。

H · 合规与风控

4 项
功能怎么实现预估效果
H1 资质与类目校验类目—资质规则表（食品、美妆、3C 等），上架前校验证照有效期与经营范围，缺件直接拦截并生成待办。避免上架后被平台下架、扣分，损失前置拦截。
H2 话术与素材合规极限词、功效宣称、医疗暗示词库做第一道规则拦截，模型复核做第二道；命中即改稿并记录命中词。合规问题在发布前解决，而不是等投诉或处罚。
H3 数据权限与脱敏字段级权限控制，手机号、地址、身份证默认脱敏；AI 只读脱敏视图，需要明文时走单独授权并留痕。客户数据不因「给 AI 看一眼」而扩散，满足最小必要原则。
H4 高危操作二次确认金额、影响 SKU 数、预算占比超阈值的动作，必须主理人二次确认（可配置为双人），确认记录进审计链。把「AI 手滑」的后果限制在可承受范围内。

4 项
功能怎么实现预估效果
I1 飞书 / 企微卡片审批卡与纪要渲染成互动卡片推送到群，卡片内直接通过 / 驳回 / 改条件，回调写回审批状态。主理人不用登录后台也能拍板，决策不再卡在「等我回电脑」。
I2 移动端审批与会议响应式布局 + 移动专用视图，会议输入框吸底、消息自动滚动到最新（原型已在 390px 验证）。路上也能开会拍板，会议不必凑时间。
I3 异常告警阈值规则（退款突增、ROI 跌破、差评词激增）+ 简单异常检测，命中即推送并自动开一个「排查任务」给对应岗位。异常从「月底发现」变成「当天发现、当天有人管」。
I4 客户端更新与版本校验electron-updater 定时拉版本清单（签名后的 latest.yml + 差分包），先校验签名与 sha512 再安装；主进程在空闲时提示，会议或任务执行中不打断，支持「稍后提醒 / 跳过此版本」；客户端版本低于强制最低版本时进入只读，可看不可写。改版从重下整包变成几 MB 差量；旧版本不会长期带着已知缺陷在线跑，也不会在开会中途被迫重启。

J4 备份与导出每日全量快照 + 增量 WAL；审计与会议纪支持导出；租户停用时按约定清除个人数据。满足交付与合规要求，客户数据可带走、可删净。
03

技术选型

一套主语言 + 三个自托管中间件

总原则：不为 47 项功能搭微服务。后端只留一门语言（Python），把不确定性收在三个自托管中间件里——LiteLLM 管模型、Langfuse 管 Prompt 与评测、Temporal 管长任务。剩下的都是业务代码。

层选型为什么是它
前端React 19 + Vite + TypeScript，由 Electron 装载；弹层与焦点管理用 Radix同一套页面既跑在桌面客户端里，也能在浏览器中调试；不引 UI 框架，避免把「纸面 + 印章红」的视觉冲掉
桌面客户端Electron（主进程 + preload + 渲染进程）；electron-builder 打包，electron-updater 差分更新Mac / Windows 各一份安装包，能拿系统通知、托盘常驻、本地文件导入；更新只推差量，不重装
状态与实时TanStack Query + Zustand；会议与任务流用 SSE发言是单向流，SSE 断线自动重连、过反代不用改配置，比 WebSocket 省事
后端Python 3.12 + FastAPI + Pydantic v2智能体生态最全；Pydantic 直接当 JSON Schema，落 C2 的六段校验与工具参数校验
长任务与状态机Temporal（起步可先用 Celery + Postgres outbox）审批等两天、会议跨多次调用，这是持久化工作流问题，不是队列问题；重试、超时、补偿开箱即用
智能体编排LangGraph任务 plan→act→check 与会议发言顺序本质是有环图，比自己写 while 循环可控、可回放
模型网关LiteLLM Proxy 自托管一次覆盖 E1/E2/E3：OpenAI 协议统一、fallback 链、预算上限、按 key 记账；书生端砚本就是 OpenAI 协议，改 base_url 即接入
Prompt / 追踪 / 评测Langfuse 自托管E4/E5 与 B4 回放一起解决：版本、灰度、trace、数据集跑分都是现成的，不用自造
结构化输出Pydantic + instructor，失败按 Schema 错误重试两次审批依据、工具参数、会议决议都强制走结构，杜绝模型自由发挥
知识库pgvector + bge-m3（TEI 部署）一个库同时解决结构化与向量，少一个中间件；中文检索够用
主库Postgres 16：事件表按月分区、行级安全做多租户业务、审批、会议、审计一处存放；J1 多租户不用另建库
缓存 / 限流 / 事件Redis 7（Streams 做事件总线、令牌桶做限流、Pub/Sub 做 SSE 扇出）三件事一个组件解决；店铺平台限流排队而不是报错
工具层MCP Python SDK + 自研注册表（白名单、参数 Schema、幂等键）G2–G5 的改价、发券、发货、发布统一收口，越权在调用前被拒
文件对象存储 OSS / S3主图、详情页、直播抽帧、审计快照
观测OpenTelemetry + Grafana（或 Sentry）J3 的 SLO 与告警；问题在客户抱怨前被发现
部署Docker Compose 起步 → 阿里云 ACK先单机跑通，别一上来就 K8s；容器化保证从沙盘到生产同一套镜像
测试Vitest + Playwright（用 _electron 直接拉起客户端调试）会议全链路（召集→发言→拍板→派发）端到端自动化，现在还是手工验的
代码组织uv workspace（后端）+ pnpm workspace（前端），单仓多包Prompt、工具、Schema 能跨服务共享，不出现两份定义

交付形态：Electron 桌面端

主形态是安装包，Mac 与 Windows 各一份；包里装的就是同一套 React 页面。浏览器只用于调试与临时访问，不做第二套界面。

部件职责注意
主进程（Node）窗口与托盘、系统通知、开机自启、自动更新、深链、本地文件读写（导入评价报表 / 商品表格）不放任何模型调用与 API Key；所有业务请求都走服务端
渲染进程就是现有 React 页面：HTTPS 调 API，SSE 收会议发言与任务进度开 contextIsolation、关 nodeIntegration，CSP 收紧到只允许自家域名
preloadcontextBridge 暴露白名单能力：通知、选文件、版本号、更新检查只暴露方法，不暴露 ipcRenderer 本体，避免渲染层拿到全量 Node 能力
发布链路electron-builder 打包 → Mac 公证 / Windows 代码签名 → 上传对象存储与版本清单 → 客户端差分更新 + 灰度首装约 100MB，后续差量几 MB；保留手动「检查更新」与强制最低版本
后端不变Python + FastAPI 仍在云上，客户端只是壳；移动端继续走飞书卡片与响应式页面换客户端不影响服务端；密钥只在服务端，客户端只持短时 token

四个取舍

不自研模型路由

LiteLLM 已经把 failover、预算、成本归集做完了。自研等于重写一遍，还更容易错。我们只维护一张「任务类型 → 档位」的策略表。

不引第二门语言

连接器、定时任务、审批回调都放同一个服务，按模块分目录，不做微服务。等单店 QPS 真撑不住再拆。

前端不套现成 UI 库

Ant Design 会把原型的视觉冲掉，且定制成本高于自写。基础交互用 Radix，样式全部自己写。

接受 Electron 的分发成本

换来系统通知、托盘常驻与本地文件能力。代价是 Mac 公证、Windows 签名、更新通道 三件需要长期维护的事，不能当成「打完包就完」。

从原型到产品

步骤做什么产出
一 · 抽令牌把原型 :root 的 CSS 变量与组件样式抽成 packages/ui，页面按路由拆成 React 组件视觉一比一，后续改一处全局生效
二 · 换假肢保留模拟引擎（时钟、队列、倍速）作为 mock adapter，接口签名与真实连接器一致没有真实店铺也能演示与演示测试
三 · 接真源按 G1 接第一个平台的授权与增量同步，先只读；写操作（改价）走 G2 的预览 + 快照只读先跑两周，再放开第一个写动作
四 · 打包分发套 Electron 壳（主进程 + preload 白名单），electron-builder 出 Mac / Windows 包，接 electron-updater 与对象存储上的版本清单双击可用的安装包；后续改版走差分更新，不用重下整包

验收指标

只留能被数字回答的
指标定义看什么目标方向
人均可控 GMV店铺 GMV ÷ 人类员工数（含主理人）平台是否真的替代了岗位，而不是把活转给另一个人随 AI 员工增加而上升

06

取舍与风险

写在前面，避免后面返工
不追求全自动

拍板权始终在人手上。用「审批 + 会议」换掉「全自动执行」，代价是多一次点击，收益是错了能停住。

模型不押注单家

书生在视觉与长上下文上合适，但旧入口有迁移期限、默认限流偏低。路由 + 降级 + 评测集三件套先行，避免把地基绑在一家身上。

合规宁可误杀

资质与话术校验先拦后放，误杀由人工放行。被误拦的成本是一分钟，被处罚的成本是一个店。

规模化前先有观测

没有 trace 与评测就扩店，等于把不确定放大。P2 的多租户必须排在 P1 的观测之后。

会议不是万能

高频、低风险的决策走审批卡即可，不必开会。会议只用于有分歧、有代价、需要多岗位对齐的事。
